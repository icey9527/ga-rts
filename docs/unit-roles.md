# 机型角色 → 3D 模型映射（S4 / T-4.0）

> 本文件是 S4 内容迁移的**输入决策**，不是运行时数据。
> 真正的运行数据是 `content/units/<角色>/unit.tbl`（T-4.1 起逐个生成）。

## 为什么要这张表

原版 Love2D 用**角色名**做单位 ID（`fighter` / `bomber` / ...），模型是
`content/units/<角色>/model.lua` 里**程序化拼装**出来的（`b:plate()` / `b:box()`）。
我们的 Godot 版用的是 S0.5 烘焙好的 **29 个 GLB**，命名是原始资产 ID（`ou05` / `ou134`）。
两边命名体系完全不同，必须先建映射，否则后面 15 个机型无从落地。

## 判定依据

1. **看图**：25 个模型各渲染 3 视角（`tools/pipeline/model-pipeline/preview/`），
   逐个看侧视与斜视，判断形状是否符合角色定位
2. **尺寸**：包围盒实测（`tools/pipeline/model-pipeline/glb_bounds.py`，读 GLB accessor 的 min/max）。
   工具已用已知数据校准：ou05 = 63.63 m / radius 31.81、ou134 = 351.74 m / radius 175.87，
   与 `unit.tbl` 里手工记录的「船长 63.6 / 351.7」完全一致
3. **原版定位**：`unit.tbl` 的 `name` / `description` 字段（中文定位描述）

## radius 口径（重要）

**radius 一律取「包围盒最长边 ÷ 2」**，不照抄原版的 `radius` 数值。
理由：我们的硬规则是「1 unit = 1 m」，半径必须是真实几何量（寻路膨胀、分离、扫掠命中全都依赖它）；
原版的 radius 是那套 2D 世界的内部单位，直接搬会与 3D 模型尺寸脱节。

原版 radius 只用于**相对排序**（谁的体量该比谁大），不用于绝对值。

## 待决策：数值缩放口径

原版与我们的数值不在同一量级：

| 量 | 原版范围 | 我们的现役值 |
|---|---|---|
| max_hp | 180 (scout) ~ 1600 (mothership) | 4200 (ou05) / 12800 (ou134) |
| speed | 0 (collector) ~ 220 (interceptor) | 180 (ou134) / 320 (ou05) |
| radius | 10 ~ 90 | 31.81 / 175.87 |

而且现役两艘**并非**从这 15 个角色迁移而来（比值不一致：
ou05 相对原版 fighter 是半径 2.29 倍、血量 14 倍、速度 2.71 倍），
所以不能用它们反推出统一缩放系数。

T-4.1 之前必须先定口径。候选方案：

- **A（推荐）血量按体量缩放**：`hp = hp_ref × (radius / radius_ref)²`，
  取 `radius_ref = 31.81`（ou05）、`hp_ref = 4200`。这样体量大的天然更耐打，
  且与「1 unit = 1 m」自洽。速度保留原版相对排序，线性映射到 180~320 m/s 区间。
- **B（保原版比例）**：全体乘同一常数（如 ×14），保留原版的相对强弱关系，
  但母舰会到 22400 hp、侦察机 2520 hp，绝对数字偏大。
- **C（人工定表）**：15 个机型逐个手填，最费时但可控。

选 A 的话需要再确认一点：`collector`（原版 speed=0、无武器）是否要作为可动单位迁移，
还是当作静态地图设施（S4 地图卡再处理）。
