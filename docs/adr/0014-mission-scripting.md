# ADR-0014 关卡编排：GDScript 协程 + 帧对比触发器（不移植字节码 VM）

- 状态：已采纳
- 日期：S1 前
- 参考：Project Sylpheed 的 SilphScript 字节码 VM 与事件系统

## 背景

Sylpheed 的关卡内容几乎全部由自研字节码脚本 VM 驱动（147 个操作码）：
事件 = 带自己 pc 的可挂起执行流，脚本里用计时器、区域触发器、生成编队、宣告胜负。
对话/语音走独立数据表（TableA），Boss 阶段由 HP 下降沿驱动。

原 Lua 2D 版的做法更简单：`plans/` 里是任务定义 + 地图脚本，胜利/失败条件写在关卡数据里。

## 选项

1. 复刻字节码 VM + 脚本编译器 —— 工程量大，且 1990 年代的做法是为省内存
2. 用 GDScript 写关卡脚本，`await` 表达可挂起执行流
3. 纯数据驱动（Resource 描述波次与条件），不写脚本

## 结论

选 2 + 3 混合：

- **流程与演出用 GDScript 脚本**（一个关卡一个脚本，继承 `MissionBase`），`await` 即"挂起执行流"，
  与 Sylpheed 的事件模型完全同构，但零 VM 成本
- **可调数据用 Resource**：波次表、对话表、Boss 阶段表、胜利条件参数
- **脚本能调的引擎能力收敛在一个 `MissionContext` 类**（生成编队 / 设目标 / 查状态 / 宣告胜负），
  不让关卡脚本直接摸 GameState —— 这是把 Sylpheed「CScriptInterpreter 116 个方法全部收口」的翻译

### 触发器用帧对比，不用 Area3D 检测回调

```
进入 = 本帧在区域内 ∧ 上帧在区域外
离开 = 本帧在区域外 ∧ 上帧在区域内
```

3D 尺度下单位一帧能飞几十米，Area3D 的 enter 信号在高速穿越时可能漏。
自己记录上帧位置做判定，成本极低，行为确定。

### 计时器作为任务原语

关卡脚本里需要大量「N 秒后做某事」。用统一的任务计时器（start / stop / is_expired / 到点触发），
而不是到处 new Timer 节点 —— 前者可暂停、可回滚、可调试，后者散落难管。

### Boss / 大型战斗的阶段切换

- 阶段由 **HP 下降沿**驱动（本帧血量 < 上帧血量 且 跨过阈值），不是单纯 `<` 判断
- 阶段切换以**动画播放完成**为节拍器，不等固定时间
- 阶段表 Resource 化：`{ hp_threshold, intro_action, on_enter[] }` 数组

### 对话三管道分离（照搬 Sylpheed）

| 管道 | 内容 | 实现 |
| --- | --- | --- |
| A 命令反馈 | 单位确认、无法执行 | signal |
| B 战况语音 | 发现敌人、被瞄准、击落 | Resource 台词池 + 防刷屏 |
| C 剧情对白 | 过场、任务简报 | 关卡脚本直接触发 |

管道 B 必须有**防刷屏四件套**：概率过滤 / 同单位同事件去重 / 一次性台词位掩码 / 有效期过期作废。
否则 RTS 里几十个单位同时喊话会吵到没法玩。

## 代价

- 关卡脚本是代码，不能由策划在编辑器里搭（但本项目是单人开发，不是问题）
- GDScript await 的调试信息不如可视化脚本

## 影响

scripts/systems/ -> 新增 mission 模块、data/maps/、scripts/core/scene_director.gd
